# Nace `application-catalog-service`

<p class="lead">Con la frontera preparada dentro del monolito, llegó el momento de crear el segundo servicio. Este capítulo explica cómo se construyó <code>application-catalog-service</code>, su base de datos propia, el <i>endpoint</i> de consulta por lotes que necesitaba el servicio de demandas y cómo se trasladaron los datos existentes.</p>

## Un proyecto nuevo con su propia base de datos [paso 5.7]

El catálogo se convirtió en un proyecto Spring Boot independiente, en `C:\Workspace\application-catalog-service`, con su propio `pom.xml`, su propio paquete raíz (`com.albertoderafael.applicationcatalog`) y su propio proceso. El código del módulo `application` del monolito se trasladó casi sin cambios: entidad, repositorio, servicio con la validación de filtros, DTO, controlador y el manejador de errores con sus cuatro casos.

```properties title="application-catalog-service/src/main/resources/application.properties" estado="final"
spring.application.name=application-catalog-service

server.port=8081

# PostgreSQL
spring.datasource.url=jdbc:postgresql://localhost:5433/application_db
spring.datasource.username=application_user
spring.datasource.password=${APPLICATION_DB_PASSWORD}

# Hibernate
spring.jpa.hibernate.ddl-auto=validate
spring.jpa.open-in-view=false

# Flyway
spring.flyway.enabled=true
```

Tres decisiones se leen en este fichero:

**Puerto 8081.** El servicio de demandas sigue en el 8080. En desarrollo, ambos procesos conviven en la misma máquina.

**Una base de datos propia, `application_db`, con un usuario propio.** El servicio no comparte tablas con nadie. El patrón se conoce como *base de datos por servicio*: cada servicio es el único dueño de sus datos, y los demás solo acceden a ellos a través de su API. Que la base de datos esté en la misma instancia de PostgreSQL (el contenedor del puerto 5433) es una comodidad de desarrollo; lo importante es la separación lógica. Con un usuario distinto, ni siquiera por error podría el servicio de demandas leer esas tablas con sus credenciales.

**Otra variable para la contraseña**, `APPLICATION_DB_PASSWORD`, distinta de la del servicio de demandas. Cada servicio tiene sus propios secretos.

::: pendiente La creación de `application_db` no está versionada
El `compose.yaml` del proyecto de demandas solo crea la base de datos `it_service_manager` y su usuario. La base de datos `application_db` y el usuario `application_user` se crearon a mano en la misma instancia, y ningún fichero del repositorio lo refleja. Quien parta de cero no podrá arrancar el catálogo sin saberlo. La solución habitual es un *script* de inicialización montado en `/docker-entrypoint-initdb.d`, que la imagen oficial de PostgreSQL ejecuta solo al crear el directorio de datos, o un servicio de base de datos propio para el catálogo. Se recoge en el capítulo 24 y **se resolvió en la fase 7** con un *script* de inicialización (capítulo 27).
:::

### Las dependencias del servicio nuevo

El `pom.xml` del catálogo usa los mismos *starters* que el monolito y añade, para las pruebas, los módulos de prueba de Spring Boot 4 que corresponden a cada uno (`spring-boot-starter-data-jpa-test`, `spring-boot-starter-flyway-test`, `spring-boot-starter-validation-test`, `spring-boot-starter-webmvc-test`) y las tres dependencias de Testcontainers. No necesita cliente HTTP: el catálogo no llama a nadie.

### La migración V1, sin datos

```sql title="application-catalog-service/…/V1__create_applications.sql" estado="final"
CREATE TABLE applications (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    name VARCHAR(100) NOT NULL,
    description VARCHAR(500),
    criticality VARCHAR(20) NOT NULL,
    status VARCHAR(20) NOT NULL
);
```

La tabla es idéntica a la del monolito, pero el servicio nuevo **no tiene migración V2** con datos iniciales. Los datos reales venían del monolito, con sus identificadores, y había que conservarlos tal cual (siguiente sección). Una V2 con datos de ejemplo habría ocupado esos identificadores o duplicado los registros.

::: java
Crear un servicio así equivale, en el mundo WebSphere, a separar un módulo EJB en su propio EAR, desplegado en su propio servidor y con su propio origen de datos. Lo que en Java EE requería coordinar con administración de sistemas aquí es un proyecto Maven, un puerto y una base de datos.
:::

## El *endpoint* de consulta por lotes [paso 5.8]

El puerto `ApplicationCatalog` tiene dos operaciones. `findById` se resuelve con el *endpoint* de detalle que ya existía. `findByIds` necesitaba uno nuevo:

```java title="application-catalog-service · ApplicationController.java (extracto)" estado="final"
@GetMapping("/summaries")
public List<ApplicationSummaryResponse> getApplicationSummaries(
        @RequestParam Set<Long> ids) {

    return applicationService.getApplicationSummaries(ids);
}
```

```java title="application-catalog-service · ApplicationService.java (extracto)" estado="final"
@Transactional(readOnly = true)
public List<ApplicationSummaryResponse> getApplicationSummaries(Set<Long> ids) {

    if (ids == null || ids.isEmpty()) {
        return List.of();
    }

    return applicationRepository.findAllById(ids)
            .stream()
            .map(application -> new ApplicationSummaryResponse(
                    application.getId(),
                    application.getName()
            ))
            .toList();
}
```

```java title="application-catalog-service · ApplicationSummaryResponse.java" estado="final"
public record ApplicationSummaryResponse(
        Long id,
        String name
) {
}
```

```json title="GET /api/applications/summaries?ids=1,2"
[
  { "id": 1, "name": "SIGMA" },
  { "id": 2, "name": "ORION" }
]
```

Varios detalles merecen explicación:

**`@RequestParam Set<Long> ids`.** Spring convierte automáticamente `ids=1,2` (valores separados por comas) o `ids=1&ids=2` (parámetro repetido) en un conjunto de `Long`. Un valor no numérico produce un 400 a través del manejador de tipos incorrectos.

**`/summaries` frente a `/{id}`.** Las dos rutas podrían coincidir con `/api/applications/summaries`. Spring MVC resuelve el conflicto eligiendo la ruta **más específica**: un segmento literal gana a una variable. Por eso `/summaries` no se interpreta como un `id` igual a `summaries`.

**Solo los que existen.** `findAllById` genera un `SELECT … WHERE id IN (…)` y devuelve solo las filas encontradas. Si se piden los `id` 1 y 99 y el 99 no existe, la respuesta tiene un elemento. Es exactamente la semántica que el puerto documenta: «los identificadores ausentes no aparecen».

**Un DTO mínimo.** La respuesta lleva solo `id` y `name`, lo que el consumidor necesita. Pedir resúmenes de cien aplicaciones no transfiere sus descripciones.

::: decision `GET` con los identificadores en la URL
**Motivo:** es una lectura idempotente que se puede almacenar en caché y depurar desde el navegador, y una página del listado tiene como mucho unas decenas de identificadores distintos. **Límite:** las URL tienen una longitud máxima práctica (del orden de miles de caracteres según servidor y *proxies*), así que no serviría para miles de identificadores. **Alternativa para ese caso:** un `POST /api/applications/summaries` con la lista en el cuerpo, que sacrifica la semántica de `GET` a cambio de no tener límite.
:::

::: atencion El parámetro es obligatorio
`@RequestParam` sin `required = false` exige el parámetro. Una petición sin `ids` produce una `MissingServletRequestParameterException`, que el manejador del proyecto no trata: llega al cliente como un 400 con el formato por defecto de Spring Boot (capítulo 10). El servicio de demandas nunca hace esa petición, porque con una página vacía no llama al catálogo, pero conviene saberlo.
:::

## Trasladar los datos existentes [paso 5.9]

Las demandas existentes apuntaban a aplicaciones por su `id`. Al mover el catálogo a otra base de datos, **los identificadores tenían que conservarse exactamente**: si la aplicación SIGMA tenía el `id` 1 en el monolito, debía tener el `id` 1 en el catálogo nuevo; si no, todas las demandas apuntarían a la aplicación equivocada.

La secuencia que encaja con los ficheros del proyecto es esta:

1. Arrancar el catálogo contra la base de datos `application_db` vacía. Flyway aplica su V1 y crea la tabla sin filas.
2. Volcar **solo los datos** de la tabla `applications` del monolito con `pg_dump`.
3. Restaurar ese volcado en `application_db`. Como la columna es `GENERATED BY DEFAULT AS IDENTITY`, PostgreSQL acepta los `id` explícitos del volcado.
4. Ajustar la secuencia de identidad con `setval`, para que la siguiente aplicación creada desde la API no reutilice un `id` existente (capítulo 4).
5. Comprobar en ambos lados que los `id` y los nombres coinciden.

::: reconstruido
El procedimiento exacto no está documentado. Se deduce de una evidencia indirecta: en la raíz del proyecto de demandas existe un fichero `applications_backup.sql` generado por `pg_dump` 18.6 que no contiene sentencias `CREATE TABLE` (es un volcado de datos) e incluye una llamada a `setval`. La guía no reproduce su contenido. El hecho de que el catálogo arranque sin una V2 de datos y que sus datos sean los de la V2 del monolito es coherente con esta secuencia.
:::

```bash title="Forma general de los comandos (ejemplo, sin credenciales)" estado="reconstruido"
# Volcar solo los datos de una tabla
pg_dump --data-only --table=applications -h localhost -p 5433 -U itmanager \
        -d it_service_manager -f applications_backup.sql

# Restaurar en la base de datos del catálogo
psql -h localhost -p 5433 -U application_user -d application_db -f applications_backup.sql
```

::: leccion Las migraciones de datos también merecen un fichero
La estructura de las bases de datos está totalmente versionada con Flyway, pero el traslado de datos entre ellas fue una operación manual. Funcionó, pero quien quiera reproducirlo, o repetirlo en otro entorno, no tiene un procedimiento escrito. Un *script* o un documento de unas líneas habría bastado. Además, el volcado quedó en la carpeta del proyecto: un fichero con datos reales que conviene excluir del control de versiones o retirar una vez cumplida su función.
:::

## Las pruebas del servicio nuevo

El catálogo nació con pruebas en los tres niveles. Las unitarias y las de capa web son las que el capítulo 11 ya explicó, más una para `/summaries`. Las de integración usan Testcontainers con la clase de Testcontainers 2:

```java title="application-catalog-service · ApplicationIntegrationTest.java (extracto)" estado="final"
@Testcontainers
@SpringBootTest
@Transactional
class ApplicationIntegrationTest {

    @Container
    @ServiceConnection
    static PostgreSQLContainer postgres =
            new PostgreSQLContainer("postgres:18")
                    .withDatabaseName("application_db")
                    .withUsername("application_user")
                    .withPassword("test");

    @Autowired
    private ApplicationRepository applicationRepository;

    @Test
    void shouldStartWithEmptyCatalogAfterFlywayMigration() {

        assertEquals(0, applicationRepository.count());
    }
}
```

La prueba `shouldStartWithEmptyCatalogAfterFlywayMigration` fija por escrito una decisión: las migraciones del catálogo crean la estructura, no datos. Si alguien añade una V2 con datos de ejemplo, la prueba falla y obliga a pensar en los identificadores.

La otra prueba de integración, `shouldCreateAndUpdateApplicationInPostgreSQL`, crea una aplicación, la modifica, llama a `flush()` para forzar el `UPDATE` contra PostgreSQL y vuelve a leerla con `findById` para comprobar los valores.

::: atencion Releer no siempre es releer
Después del `flush()`, la prueba no llama a `clear()`. La entidad sigue en el contexto de persistencia, así que `findById` la devuelve **desde la memoria**, sin ir a la base de datos. La prueba demuestra que el `UPDATE` es SQL válido (si fallara, `flush()` lanzaría una excepción), pero no que los valores leídos vengan de PostgreSQL. Para eso haría falta `entityManager.clear()` entre el `flush()` y la lectura, como hacen las pruebas de integración del servicio de demandas.
:::

## Errores típicos y depuración

| Síntoma | Causa probable | Cómo resolverlo |
|---|---|---|
| `database "application_db" does not exist` | La base de datos del catálogo no se creó en la instancia | Crearla, o añadir un *script* de inicialización |
| `Port 8081 was already in use` | Otra instancia del catálogo sigue arrancada | Pararla |
| `/summaries` responde 400 «Invalid value for parameter: id» | La petición llegó a `/{id}` por un error en la ruta | Revisar la URL exacta |
| Las demandas muestran nombres de otras aplicaciones | Los `id` no se conservaron al trasladar los datos | Restaurar con los `id` originales |
| `duplicate key … applications_pkey` al crear una aplicación | No se ajustó la secuencia tras la importación | Ejecutar `setval` con el máximo `id` |
