# El modelo de la demanda

<p class="lead">El segundo módulo introduce dos cosas que el primero no tenía: una relación con otra entidad y reglas de negocio que dependen del estado. Este capítulo explica la tabla <code>demands</code>, la entidad tal como era en el monolito, sus fechas y la máquina de estados que gobierna su ciclo de vida.</p>

## Qué es una demanda

Una demanda es una petición de trabajo sobre una aplicación del catálogo: una mejora, una adaptación normativa, un cambio. Tiene título, descripción opcional, prioridad, estado y, siempre, una aplicación a la que pertenece. A diferencia de una aplicación, una demanda **evoluciona**: se abre, se trabaja en ella, se completa o se cancela, y no todos los cambios de estado tienen sentido.

| Atributo | Tipo | Reglas |
|---|---|---|
| `title` | Texto, máx. 150 | Obligatorio |
| `description` | Texto, máx. 1000 | Opcional |
| `priority` | `LOW`, `MEDIUM`, `HIGH`, `CRITICAL` | Obligatoria |
| `status` | `OPEN`, `IN_PROGRESS`, `COMPLETED`, `CANCELLED` | Lo fija el servidor al crear; cambia según reglas |
| aplicación | Referencia a `applications` | Obligatoria y debe existir |
| `createdAt`, `updatedAt` | Instantes en UTC | Los fija el servidor |

## La migración V3 crea `demands` [paso 3.1]

```sql title="V3__create_demands.sql" estado="impl"
CREATE TABLE demands (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,

    title VARCHAR(150) NOT NULL,
    description VARCHAR(1000),

    priority VARCHAR(20) NOT NULL,
    status VARCHAR(20) NOT NULL,

    application_id BIGINT NOT NULL,

    created_at TIMESTAMP WITH TIME ZONE NOT NULL,
    updated_at TIMESTAMP WITH TIME ZONE NOT NULL,

    CONSTRAINT fk_demands_application
        FOREIGN KEY (application_id)
        REFERENCES applications(id)
);

CREATE INDEX idx_demands_application_id
    ON demands(application_id);

CREATE INDEX idx_demands_status
    ON demands(status);

CREATE INDEX idx_demands_priority
    ON demands(priority);
```

**La clave foránea.** `fk_demands_application` garantiza en la base de datos que toda demanda apunta a una aplicación existente. Su nombre explícito no es un capricho: para eliminarla algún día con `ALTER TABLE … DROP CONSTRAINT` hay que conocerlo, y si PostgreSQL lo hubiera generado, dependería de sus reglas internas. No tiene `ON DELETE`, así que PostgreSQL impide borrar una aplicación con demandas, lo cual encaja con la decisión de no borrar aplicaciones (capítulo 9).

**Los índices.** PostgreSQL crea automáticamente un índice para la clave primaria, pero **no** para las claves foráneas. El índice sobre `application_id` acelera el filtro «demandas de esta aplicación», que el frontend usa en la ficha de cada aplicación, y las comprobaciones de integridad. Los índices sobre `status` y `priority` corresponden a los otros dos filtros del listado.

**`TIMESTAMP WITH TIME ZONE`.** A pesar del nombre, PostgreSQL no guarda la zona horaria: convierte el valor a UTC al escribir y lo devuelve en la zona de la sesión al leer. Es decir, guarda **un instante** en el tiempo, sin ambigüedad. Hibernate 6 y posteriores asocian por defecto el tipo `java.time.Instant` a este tipo de columna, de modo que `ddl-auto=validate` los acepta como compatibles.

::: decision Fechas como instantes en UTC
**Motivo:** un instante no depende de dónde esté el servidor ni el usuario; el frontend lo muestra en la hora local del navegador. **Alternativa descartada:** `TIMESTAMP` sin zona con `LocalDateTime`, que guarda una fecha y hora «de pared» sin referencia: dos servidores en zonas distintas, o un cambio de horario de verano, producen valores ambiguos.
:::

## La entidad `Demand` en el monolito [paso 3.2]

En el monolito, la demanda se relacionaba con la aplicación a través de una **asociación JPA**: la entidad tenía un atributo de tipo `Application`, no un número.

```java title="demand/entity/Demand.java (versión del monolito)" estado="reconstruido"
@Entity
@Table(name = "demands")
public class Demand {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @Column(nullable = false, length = 150)
    private String title;

    @Column(length = 1000)
    private String description;

    @Column(nullable = false, length = 20)
    private String priority;

    @Column(nullable = false, length = 20)
    private String status;

    @ManyToOne(fetch = FetchType.LAZY, optional = false)
    @JoinColumn(name = "application_id", nullable = false)
    private Application application;

    @Column(name = "created_at", nullable = false)
    private Instant createdAt;

    @Column(name = "updated_at", nullable = false)
    private Instant updatedAt;

    protected Demand() {
        // Constructor requerido por JPA
    }

    public Demand(String title, String description, String priority,
                  String status, Application application) {
        this.title = title;
        this.description = description;
        this.priority = priority;
        this.status = status;
        this.application = application;
    }

    public void update(String title, String description, String priority,
                       Application application) {
        this.title = title;
        this.description = description;
        this.priority = priority;
        this.application = application;
        this.updatedAt = Instant.now();
    }

    // prePersist, changeStatus y getters: igual que en la versión final
}
```

::: reconstruido
Esta versión ya no existe: la fase 5 sustituyó la asociación por un identificador (capítulo 18). Se reconstruye a partir de tres fuentes del propio proyecto: el documento `frontera-catalogo.md`, que dice que tras el refactor «la entidad ya no contiene una asociación JPA hacia Application» y que «las pruebas de dominio usan identificadores»; la mención a una prueba que verificaba un `EntityGraph` sobre esa asociación; y la entidad final, que conserva el resto de atributos y métodos. Los detalles de anotación (`LAZY`, `optional = false`) son los que exige el diseño descrito en el capítulo 14, pero no pueden verificarse literalmente.
:::

### Qué significa cada anotación de la asociación

**`@ManyToOne`.** Muchas demandas pertenecen a una aplicación. En la tabla es la columna `application_id`; en Java, una referencia al objeto.

**`@JoinColumn(name = "application_id")`.** Indica qué columna contiene la clave foránea.

**`fetch = FetchType.LAZY`.** En JPA, las asociaciones `@ManyToOne` son **`EAGER` por defecto**: al cargar una demanda, Hibernate carga también su aplicación, siempre, se necesite o no. Con `LAZY`, Hibernate coloca en el atributo un **proxy**: un objeto de una subclase generada de `Application` que solo conoce el `id`. La primera vez que se llama a un método como `getName()`, el proxy ejecuta el `SELECT` de la aplicación. Esto exige que el contexto de persistencia siga abierto; con `open-in-view=false`, fuera de la transacción ese acceso lanza `LazyInitializationException`.

**`optional = false`.** Informa a Hibernate de que la asociación nunca es nula, lo que le permite usar uniones internas en lugar de externas al consultarla.

::: atencion `EAGER` por defecto es una trampa
Dejar `@ManyToOne` con su valor por defecto parece cómodo, pero hace que cualquier consulta de demandas arrastre consultas adicionales de aplicaciones, también cuando no se van a usar. La práctica recomendada es declarar todas las asociaciones `LAZY` y decidir en cada consulta qué se carga, que es lo que el proyecto hizo con `@EntityGraph` (capítulo 14).
:::

## Las fechas de creación y modificación

La versión final de la entidad, que en esta parte coincide con la del monolito, gestiona las fechas así:

```java title="demand/entity/Demand.java (extracto)" estado="impl"
@PrePersist
private void prePersist() {
    Instant now = Instant.now();
    this.createdAt = now;
    this.updatedAt = now;
}
```

`@PrePersist` es una **retrollamada del ciclo de vida** de JPA: Hibernate ejecuta el método justo antes de insertar la entidad. Puede ser privado. Las dos fechas reciben el mismo instante, de modo que una demanda recién creada tiene `createdAt == updatedAt`.

La fecha de modificación, en cambio, no se gestiona con `@PreUpdate`, sino a mano: `update(...)` y `changeStatus(...)` asignan `updatedAt = Instant.now()`.

::: decision `updatedAt` explícito en los métodos de negocio
**Motivo:** la fecha cambia exactamente cuando cambia la demanda a través de una operación de negocio, y la respuesta del servicio ya lleva la fecha nueva, porque se asigna antes de construir el DTO. Con `@PreUpdate`, la fecha se asignaría durante el *flush*, que ocurre **después** de construir la respuesta: el cliente recibiría la fecha antigua. **Alternativas:** `@PreUpdate`; las anotaciones de Hibernate `@CreationTimestamp` y `@UpdateTimestamp`; o la auditoría de Spring Data (`@CreatedDate`, `@LastModifiedDate`). **Coste:** cada nuevo método que modifique la demanda debe acordarse de actualizar la fecha.
:::

Una consecuencia sutil: `update(...)` asigna la fecha aunque los valores recibidos sean idénticos a los actuales. La entidad queda «sucia» por el cambio de `updatedAt` y Hibernate emite un `UPDATE` en cada petición `PUT`, cambie algo o no.

```java title="demand/entity/Demand.java" estado="impl"
public void changeStatus(String newStatus) {

    if (this.status.equals(newStatus)) {
        return;
    }

    boolean validTransition =
            ("OPEN".equals(this.status)
                    && ("IN_PROGRESS".equals(newStatus)
                        || "CANCELLED".equals(newStatus)))
            ||
            ("IN_PROGRESS".equals(this.status)
                    && ("COMPLETED".equals(newStatus)
                        || "CANCELLED".equals(newStatus)));

    if (!validTransition) {
        throw new IllegalStateException(
                "Invalid demand status transition: "
                        + this.status + " -> " + newStatus
        );
    }

    this.status = newStatus;
    this.updatedAt = Instant.now();
}
```

Las reglas son cuatro transiciones válidas, y todo lo demás es inválido:

| Desde | Hacia | Resultado |
|---|---|---|
| Cualquiera | El mismo estado | Se acepta sin hacer nada |
| `OPEN` | `IN_PROGRESS` o `CANCELLED` | Se aplica |
| `IN_PROGRESS` | `COMPLETED` o `CANCELLED` | Se aplica |
| `COMPLETED` o `CANCELLED` | Cualquier otro | `IllegalStateException` |
| `IN_PROGRESS` | `OPEN` | `IllegalStateException` |

Que repetir el estado actual no sea un error tiene una razón práctica: el formulario de modificación envía siempre el estado. Si el usuario solo cambia el título, el estado llega igual que estaba, y eso no debe rechazarse.

::: decision La regla vive en la entidad
**Motivo:** la entidad es el único sitio por el que pasa cualquier cambio de estado, así que la regla no se puede saltar desde ningún servicio. Además se prueba con pruebas unitarias puras, sin *mocks* ni Spring. **Alternativa descartada:** comprobar las transiciones en el servicio, donde cualquier otro código con acceso a la entidad podría cambiarle el estado directamente. **Detalle:** la entidad lanza `IllegalStateException`, una excepción de Java sin relación con HTTP; es el servicio quien la traduce a un 409 (capítulo 15).
:::

### Las pruebas del dominio

```java title="demand/entity/DemandTest.java (extracto)" estado="final"
class DemandTest {

    private final Long applicationId = 1L;

    @Test
    void shouldRejectInProgressToOpen() {

        Demand demand = createDemand("IN_PROGRESS");

        assertThrows(
                IllegalStateException.class,
                () -> demand.changeStatus("OPEN")
        );

        assertEquals("IN_PROGRESS", demand.getStatus());
    }

    @Test
    void shouldAllowSameStatus() {

        Demand demand = createDemand("OPEN");

        assertDoesNotThrow(() ->
                demand.changeStatus("OPEN"));

        assertEquals("OPEN", demand.getStatus());
    }

    private Demand createDemand(String status) {
        return new Demand(
                "Demanda test",
                "Descripción de prueba",
                "HIGH",
                status,
                applicationId
        );
    }
}
```

La clase tiene cinco pruebas: dos transiciones válidas, dos inválidas y la repetición del estado. Cada prueba inválida comprueba también que **el estado no cambió** tras la excepción. En la versión final, la demanda se crea con un identificador de aplicación; en el monolito, con un objeto `Application`, como recoge el documento del refactor.

::: pendiente Huecos en las pruebas del ciclo de vida
Ninguna prueba cubre las transiciones hacia `CANCELLED` ni el rechazo de salidas desde `CANCELLED`. Son reglas tan importantes como las demás. El ejercicio 12.1 propone completarlas.
:::

## Errores típicos y depuración

| Síntoma | Causa probable | Cómo resolverlo |
|---|---|---|
| Las fechas aparecen desplazadas una o dos horas | Se mezclaron fechas sin zona (`LocalDateTime`) con instantes | Usar `Instant` en todo el recorrido y convertir a hora local solo al mostrar |
| Cada demanda cargada dispara un `SELECT` de su aplicación | La asociación se dejó `EAGER` por defecto | Declararla `LAZY` (y ver el capítulo 14) |
| `LazyInitializationException: could not initialize proxy` | Se accede a la aplicación fuera de la transacción | Construir el DTO dentro del servicio o cargarla con la consulta |
| `createdAt` es `null` al insertar | Se olvidó `@PrePersist` o el método no se ejecutó | Comprobar la anotación y que se inserta con JPA |
| Un `PUT` sin cambios genera un `UPDATE` | `update(...)` siempre asigna `updatedAt` | Comportamiento esperado con este diseño |
