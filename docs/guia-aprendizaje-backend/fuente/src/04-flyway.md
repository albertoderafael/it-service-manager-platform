# Migraciones de esquema con Flyway

<p class="lead">El esquema de la base de datos se trata como código: cada cambio es un fichero SQL numerado, versionado con el resto del proyecto y aplicado automáticamente al arrancar. Este capítulo explica cómo lo hace Flyway, las dos primeras migraciones y las reglas que evitan los problemas más serios.</p>

## Por qué migraciones versionadas

Sin una herramienta de migraciones, el esquema de cada entorno evoluciona a mano: alguien ejecuta un `ALTER TABLE` en desarrollo, otro lo olvida en pruebas y nadie sabe con certeza qué versión tiene producción. Flyway resuelve tres problemas a la vez:

1. **Reproducibilidad.** Una base de datos vacía llega siempre al mismo esquema aplicando las mismas migraciones en el mismo orden.
2. **Trazabilidad.** Cada cambio tiene un fichero, un número y un autor en el control de versiones.
3. **Automatización.** La aplicación aplica las migraciones pendientes al arrancar; no hay pasos manuales que olvidar.

::: java
En muchos proyectos Java EE los cambios de esquema se entregaban como *scripts* al equipo de base de datos, que los aplicaba en cada entorno. Flyway formaliza ese mismo flujo y lo automatiza, y añade lo que solía faltar: un registro, dentro de la propia base de datos, de qué *scripts* se han aplicado ya.
:::

## Cómo funciona Flyway por dentro

Flyway busca las migraciones en `src/main/resources/db/migration`. El nombre de cada fichero sigue un patrón estricto:

```text
V2__insert_initial_applications.sql
│ │  └─ descripción (los guiones bajos se leen como espacios)
│ └──── dos guiones bajos como separador
└────── V de «versionada» + número de versión
```

Al arrancar, la autoconfiguración de Spring Boot ejecuta Flyway **antes** de crear el `EntityManagerFactory` de JPA. Flyway hace lo siguiente:

1. Si no existe, crea la tabla **`flyway_schema_history`**.
2. Lee de esa tabla qué versiones están aplicadas y con qué *checksum* (una huella calculada a partir del contenido de cada fichero).
3. Compara con los ficheros disponibles. Si el *checksum* de una migración ya aplicada no coincide con el de su fichero, **se detiene con un error de validación**.
4. Aplica en orden las migraciones pendientes, cada una en su propia transacción, y registra cada una en la tabla de historial.

Después, Hibernate valida el esquema resultante (`ddl-auto=validate`). El orden garantiza que Hibernate siempre valida un esquema ya migrado.

## La migración V1 crea `applications` [paso 1.5]

```sql title="V1__create_applications.sql" estado="impl"
CREATE TABLE applications (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    name VARCHAR(100) NOT NULL,
    description VARCHAR(500),
    criticality VARCHAR(20) NOT NULL,
    status VARCHAR(20) NOT NULL
);
```

Tres detalles de esta migración se reflejan después en el código Java:

**La clave primaria es una columna de identidad.** `GENERATED BY DEFAULT AS IDENTITY` es la forma estándar de SQL para un autoincremento; sustituye al antiguo tipo `BIGSERIAL` de PostgreSQL. PostgreSQL asigna el valor al insertar la fila. En la entidad le corresponde `@GeneratedValue(strategy = GenerationType.IDENTITY)` (capítulo 5).

La variante `BY DEFAULT`, frente a `ALWAYS`, permite insertar una fila indicando el `id` explícitamente. Es útil para importar datos que ya tienen identificadores, pero tiene una trampa: la secuencia interna no avanza con esas inserciones manuales, y la siguiente inserción normal puede intentar reutilizar un `id` existente. Tras una importación hay que ajustar la secuencia, normalmente con `setval`.

**Las longitudes coinciden con las validaciones.** `VARCHAR(100)` para el nombre corresponde a `@Column(length = 100)` en la entidad y a `@Size(max = 100)` en el DTO de entrada (capítulo 8). Si los tres no coinciden, el error aparece tarde y en el sitio equivocado: una cadena de 120 caracteres pasaría la validación y fallaría en el `INSERT` con un error de base de datos.

**Estado y criticidad son texto.** No hay tipo enumerado de PostgreSQL ni restricción `CHECK`: los valores válidos se controlan en Java. Es una decisión consciente, con un coste que se discute en el capítulo 8.

## La migración V2 carga las aplicaciones iniciales [paso 1.6]

```sql title="it-service-manager/…/V2__insert_initial_applications.sql" estado="impl"
INSERT INTO applications (
    name,
    description,
    criticality,
    status
)
VALUES
(
    'SIGMA',
    'Portal de gestión de expedientes',
    'HIGH',
    'ACTIVE'
),
(
    'ORION',
    'Aplicación backend',
    'MEDIUM',
    'ACTIVE'
);
```

Una migración no tiene por qué cambiar la estructura: también puede cargar datos de referencia. Aquí se insertan las dos primeras aplicaciones del catálogo, de modo que una base de datos recién creada ya tiene algo que mostrar en el frontend. Los `id` no se indican; los asigna la columna de identidad.

### La copia pública y su V2 distinta

Al preparar la versión publicada en GitHub se sustituyeron esos datos por registros ficticios:

```sql title="it-service-demand-manager/…/V2__insert_initial_applications.sql" estado="impl"
-- Fictional sample records for a new demonstration database.
INSERT INTO applications (name, description, criticality, status)
VALUES
    ('Portal de ejemplo', 'Portal ficticio de servicios internos', 'HIGH', 'ACTIVE'),
    ('API de ejemplo', 'Servicio backend ficticio', 'MEDIUM', 'ACTIVE');
```

El nombre del fichero es el mismo, pero el contenido no, así que su *checksum* tampoco. Si alguien arrancara la copia pública contra la base de datos original, Flyway encontraría la V2 registrada con un *checksum* y el fichero con otro, y se negaría a arrancar. La guía de instalación del repositorio lo advierte explícitamente y pide usar una base de datos nueva.

::: leccion Una migración aplicada es inmutable
Este episodio ilustra la regla más importante de Flyway: **una migración que ya se aplicó en alguna base de datos no se modifica nunca**. Si hay que corregir algo, se crea una migración nueva. La copia pública es un caso legítimo, porque está pensada para bases de datos nuevas, pero muestra exactamente qué ocurre cuando un fichero aplicado cambia.
:::

## Las reglas que evitan problemas

| Regla | Por qué |
|---|---|
| No modificar migraciones aplicadas | Rompe la validación de *checksums* en todas las bases de datos que ya la tienen |
| Solo hacia delante | Flyway Community no deshace migraciones; para revertir un cambio se escribe otra migración que lo revierta |
| Una migración, un propósito | Facilita entender el historial y localizar el origen de un problema |
| Probar en una base de datos vacía | Garantiza que la secuencia completa V1…Vn funciona desde cero |
| No usar `repair` para «arreglar» un *checksum* | `repair` reescribe el historial para que coincida con los ficheros: oculta la discrepancia, no la resuelve |

::: atencion `clean` borra todo
Flyway tiene un comando `clean` que elimina **todos** los objetos del esquema. Spring Boot lo mantiene desactivado por defecto (`spring.flyway.clean-disabled=true`). No lo actives en una base de datos con datos que quieras conservar.
:::

::: decision SQL escrito a mano en lugar de generado
**Motivo:** el SQL de las migraciones es exactamente el que se ejecutará en todos los entornos; se revisa como cualquier otro código y aprovecha la sintaxis de PostgreSQL. **Alternativas descartadas:** dejar que Hibernate genere el esquema (`ddl-auto=update`), sin historial ni control; o Liquibase, válido y con más funciones (*changelogs* en XML o YAML, *rollbacks*), pero más complejo de lo que el proyecto necesitaba.
:::

## Errores típicos y depuración

| Síntoma | Causa probable | Cómo resolverlo |
|---|---|---|
| `Validate failed: Migration checksum mismatch for migration version 2` | Se modificó un fichero ya aplicado | Restaurar el contenido original y crear una migración nueva con el cambio |
| `Detected resolved migration not applied to database` | Hay una migración con número menor que la última aplicada | Renumerarla por encima de la última, o revisar el orden |
| Una migración nueva no se ejecuta | El nombre no sigue el patrón (un solo guion bajo, falta la `V`) | Corregir el nombre: `V3__descripcion.sql` |
| `relation "applications" does not exist` al arrancar | Flyway no se ejecutó (falta el *starter* en Spring Boot 4) | Ver el capítulo 2 |
| `duplicate key value violates unique constraint "applications_pkey"` | Se insertaron filas con `id` explícito sin ajustar la secuencia | Ajustar la secuencia con `setval` |

## Ejercicios

::: ejercicio Leer el historial
Conéctate a la base de datos y ejecuta `SELECT installed_rank, version, description, checksum, success FROM flyway_schema_history ORDER BY installed_rank;`. Identifica la fila de cada migración e interpreta cada columna.
:::

::: ejercicio Diseñar una migración correctiva
Supón que quieres impedir en la base de datos que `criticality` tome valores distintos de LOW, MEDIUM, HIGH y CRITICAL. Escribe (sin aplicarla en la base de datos real) la migración que lo haría, con su nombre de fichero correcto, y explica por qué no se puede añadir esa restricción editando la V1.
:::

::: preguntas
1. ¿Qué guarda la tabla `flyway_schema_history` y para qué usa Flyway el *checksum*?
2. ¿En qué orden se ejecutan Flyway y la validación de Hibernate al arrancar, y por qué importa?
3. ¿Qué diferencia hay entre `GENERATED BY DEFAULT AS IDENTITY` y `GENERATED ALWAYS AS IDENTITY`?
4. ¿Por qué la copia pública del repositorio no debe conectarse a la base de datos original?
5. ¿Por qué no es buena idea usar `flyway repair` para resolver un error de *checksum*?
:::
